# 数据库与库存事务

主要实现：`src/component_library/database.py`；公共请求模型：`models.py`。

## 数据模型与命名兼容

- `components`：元件主数据，类别参数另存在相应扩展表中。
- `warehouses`：**旧内部名称**，在 UI 实际表示上级“位置”。
- `locations` 表示界面中的具体仓库，通过 `warehouse_id` 关联上级位置。`color` 保存 RGB 色标，迁移为已有仓库分配默认值。
- `stock_lots`：入库批次及剩余数量。
- 库存事务流水：记录入库、出库、调拨、调整、冲销等历史。
- 订单去重、API 幂等与网页缓存等记录由数据库维护。

不要仅为了改 UI 名词直接重命名 API 字段、表或旧列，否则会破坏兼容性。

## 写事务与不变量

`Database.write()` 使用 `BEGIN IMMEDIATE`，确保并发请求的检查与扣减是单个事务。核心保证：

1. 库存数量为整数，批次剩余量不可为负。
2. 出库在事务内检查可用量并按 `received_at, id` 确定 FIFO 顺序。
3. BOM 领料、订单导入与批量移库都在单次业务事务中提交，任何一行失败都会回滚整组。
4. 移库按库存批次 ID 与预览余量校验，目标库存保留采购及入库时间，成对流水记录实际移库时间。错误用独立冲销操作更正。
5. 删除有库存的元件被拒绝；历史元件可能安全归档。

## 修改数据库

- 先增加失败测试：旧库兼容、重复迁移、库存边界、异常回滚。
- 在现有迁移机制中追加**可重复执行**的迁移；勿改既有列的业务语义。
- 保持 WAL 和外键约束；迁移前有快照保护，但不能代替测试与人工备份。
- 始终走 `Database` 公共服务，而不是从 UI/解析器直接 `UPDATE stock_lots`。

## 扩展事务的建议步骤

先在 `models.py` 定义输入校验，再在 `Database` 中实现最小原子操作；补并发/回滚及库存边界测试，最后由 UI 或 API 暴露。若写 API，还需通过 `ApiContext.mutate()` 使用幂等键。

相关测试：`tests/test_database.py`、`tests/test_api.py`、`tests/test_order_import.py`。
